# AI 小说写作平台

这是一个 Electron + React 桌面小说创作平台，后端使用 NestJS + SQLite。目标是支持短篇与长篇从灵感、架构、大纲、正文生成到质量检查、连续性维护和长期创作。

## 唯一执行标准

项目的小说生成规则、质量 Gate、修复原则和验收方式只在 [执行标准](server/shared/src/执行标准.ts) 维护；应用内“执行标准”和运行时读取同一来源。

README 不重复标准内容，也不维护标准版本号。代码中的扫描器、Creative Constitution、ChapterPlan、平台基准和模块 seed 都是该标准的可执行实现。

灵感发现先锁定作者选择、平台分类、字典来源和历史排除项，并发生成轻量故事候选；每个原池生成批次在同一次调用中按已有事件完成成熟度评分与排序，并在全池选优、初次已选题材的审核与成卡派发、原池汇总重选以及缺额补位时沿用高分优先顺序；原池重选需要的新身份已带真实来源因果索引时复用既有严格投影与标准化器直接选出原池备用，无需再次调用模型选身份，所有独立审核和内容质量门不变，来源不足则走原有有界模型路径；评分只依据原池已写事件及实际因果、阅读价值给出，缺乏事实依据的维度不得凭模型自述加分；它只用于任务优先级与备用顺序，缺失分数保留未知，原独立质量门不变，每批返回即同步完成确定性结构与命名检查，批间仍按原身份稳定合并，全池统一选优及独立审核，不新添评分模型调用。跨分类生成和缺额补位按每项锁定分类取得投稿标签候选，生成前核对所有必要分类的标签来源，缺失时在模型调用前明确报错；与接收校验同源。自动选择的标签、基调、文风和视角随候选一次确定并保存；选优与成卡继承同一候选，不重新决定这些选项。固定原池选优只选择身份与现有事实的因果引用，原池分句附带可复制的sourceRef；同节连续区间由同一目录和解析器定位，历史模型重复同节端点（含两端各自带方括号的原池标记）仅在同身份、同节、顺序和真实边界均有效时兼容，跨题材、跨分节及虚构地址仍拒绝。服务器按原池还原原文和字段，不改变故事来迎合引用；编号正确只证明原池地址可追溯；五节结构有效数量不等于因果成熟数量。选优、原池重选与独立前审对每一项已声称兑现的独立结果核对决定者、实际采纳依据及生效动作，不能用查明主要问题自动推出附带的处分、资格或利益改变；后续完整卡仍独立验收因果和阅读质量。分类有公开写作说明时由同一来源供生成、选优与审核使用，公开说明与投稿后台分类、体量和收益证据分别记录。

来源继承、因果成立、分类与全部流派落实、题材差异和完整卡阅读质量分别验收。固定分节的原样投影由程序逐字验证；新写字段和任何无法证明的内容仍接受独立来源审核，程序证明不代表语义质量通过。审核分组按实际工作量分配并按原身份绑定证据，不要求候选相邻；缺口审核遗漏修复路线时按同ID原池的逐字证据保守归类，仍保留gap和独立复核，不因JSON字段遗漏增加调用或放行；同版本模型元数据的多次调用只作未证实重复的诊断备注，不当成故障警告；明确编号的同一原文投影与字段别名、拒绝理由封装由程序无歧义归一；已明确gap的空条件引用按未提供处理并保留拒绝，不增加模型调用、不改变质量判定。候选与选优接收作者已选维度的同源执行要求；前置已证明缺额且原预算足够时，同一补位波次提前选优和来源准备，补位完整卡仍等待首轮身份核对；补位原池与已有原池选优共享首轮已举证的真实淘汰原因及后来完整卡拒绝原因，不把协议失败当作内容不足，也不新增审核流程。每项完成原有前置质量门后即可接续成卡，完整卡在已预留逐卡终审额度时即时进入同一限流队列，只预留整体审核的短批仍合并终审；缺卡补位复用同一调度，全部阶段共享原预算和并发上限，不因纠错增加额度。未审、未知、拒绝和停止项不计合格；只有达到本次请求数量且完整卡全部终审通过才报告完成。详细合同由唯一执行标准定义，响应见 [API 文档](server/docs/API.md)，操作见 [用户指南](server/docs/user-guide.md)。本轮真实生产以唯一执行标准规定的整次请求墙钟上限为性能验收目标，且动态足额交付及全部质量 Gate 通过；性能目标只在运行结束后评估，正式生成不会到时自动取消或清空合格卡，单次模型超时、原调用预算与质量要求不变。必须用同版本、同模型的新运行证明，CI不能代替。


轻量候选同次生成先从结局逆查实际条件、作用边界及对手反制，不成熟槽位当次重新构思，不能依赖后续淘汰和补位制造质量；五节有效性与因果源地址使用同一解析器；初始原池和缺额补位共用有界JSON回收及生成前槽位校验，单个补位批次失败不丢弃其它批次有效结果；生成器以五个具名节块传输，服务器仅将模型实际写出的原文无损归为一份 `storyCore`，旧完整正文格式继续兼容，缺节、冲突或质量不足仍按原Gate拒绝并记录具体原因，不保留第二份故事事实；重复/乱序节及把主动选择、必要条件、兑现写成相同事实的胚子在付费选优前淘汰；同一次汇总重选只隔离有无效引用的替换项，其他结构合格项仍须完成全部独立审核，不因个别引用错误清空整批。候选引用纠错仅等待受影响的原审核组，其它组及差异审核并行；已审核细纲的展示字段直接投影，旧资料缺结构时沿用原兼容补全；详细章纲若误写成长段章节对白正文，先用原有结构纠错还原事件链，不将正文篇幅误作章纲计划，也不删减关键因果或新增审核调用；内部评分及证据补全继承原始截止时间。角色前移只建立当前基准，不封死后续人物补充；新人物沿用有据引入、候选确认和事实不倒改的标准。长篇创建在主线骨架和世界规则的原有生成节点核对已有必要结构与核心事实，缺失时不继续消耗角色和细纲调用；已确认原始题材继续作为角色和章纲生成的只读上层事实，不只依赖骨架改述；短长篇主视角角色按已确认题材与骨架身份识别，短篇恢复核对主角、核心人物和扩展档案，人物批次原子写入失败时回滚；长篇在骨架节点核对已确认具名主角、世界规则无损写入与冻结恢复，力量体系说明不冒充缺失规则；长篇已有章纲事实复核同批读取主世界、关联规则档案与角色身份能力关系，允许无独立因果规则的长篇保留空数组，同时继续拒绝短篇缺失核心规则或规则格式错误；长篇创建及滚动章纲保留完整角色动机、能力、关系，跨卷伏笔读取完整已生成章纲事件，避免以标题代替事实；短篇实际创建入口依次为已确认题材→世界规则→人物→故事闭环与全书章节职责→逐章详细章纲→整体验收与保存→组织地点/伏笔/时间线→激活；结构有效、带原生成凭证的未确稿章纲只存于原有非正式检查点，后续评审因网络/协议不可用时按同一输入指纹复用并完整重审，已证事实或行动缺口不得原样复用；世界规则与人物各传一次权威上下文，补充环境只传未重复的场景字段；rules逐项核对已确认题材而不是一次整体判定；原角色生成步骤前移，章纲读取已保存人物，不在章纲完成后另生角色。候选槽位直接携带其同源分类执行要求，原池与补位共用；人物关键泄密、让步和决定从候选起使用与规划、细纲、正文及审核相同的判据，候选必要条件须覆盖实际结果。结构化纠错与质量重试继承同一原始时限；前置章节条件按当前及前章的实际行动地址核对，不接受后章或出口结果自证；章节必要取得动作缺失按原有章责修复路径处理，不虚构世界规则冲突，也不放行未处理的条件缺口。成卡提示与流派定义使用该候选已锁定的选项；历史缺项只为缺少的字段提供原有选择指令。仅修正因果引用的复核保留同一决定依据判据。候选生成与前审共用决定依据判据；关键环节依赖他人改变决定时，前审需引用原候选中的决定者及采纳依据，缺证据不能进入成卡。短篇规划在同次生成中返回与长篇相同的完整章节合同；必要条件、时间边界及出口状态经过前审后，原样传到职责修订、细纲、保存和正文读取。创建阶段只投影已确认故事所需规则，候选池重选和缺额调度说明留在灵感发现阶段；具体判据仍由唯一执行标准定义。长短篇创建共用的故事地基保留已确认完整卡的结局和阶段规划；创建事实与行动首审通过原文中的细分证据地址逐项核对同一条目中的并列结果；条件从句与所限定的结果保留同一地址，不把前提单独当成已兑现结果；事实补丁保留可唯一定位的短引文，不把同字段周围的改动当作修复，不以局部事件证明未出现的社会评价；同时定位原文的时刻与时长，沿原有事实合同完成核对。跨模块一致性审核的点号或方括号数组索引统一绑定到原始完整数组中的真实章节、人物等身份；即使章节证据已定位，聚焦修订仍保留同一冲突点名的relationships与profile_json等依赖字段，不误带无关人物；候选同批修订、复查通过后事务写入。

## 主要入口

- `/`：创作质量看板
- `/projects`：项目管理
- `/discover`：灵感发现与项目创建主入口
- `/module-standards`：当前运行规则只读视图
- `/project/:id/dashboard`：单本作品看板
- `/project/:id/world`：世界观
- `/project/:id/characters`：角色
- `/project/:id/outline`：大纲
- `/project/:id/writing`：正文写作
- `/project/:id/conflicts`：冲突/矛盾
- `/project/:id/writing-quality`：质量报告
- `/project/:id/refinement`：精修

长篇首次创建通过 `long-novel-init-foundation` 建立主线骨架与世界规则，然后由创建流程自身生成角色和首批详细章纲；后续详细章纲随正文推进按需滚动补足；在「大纲 → 章节列表」可从下拉框选择补充 1、3、5、10 章并点击「补充章纲」；「全书骨架」是独立的结构入口，分为世界观、主线及卷纲、人物势力、伏笔和时间线，不把章节列表当成全书骨架；短中长伏笔、卷伏笔和全书伏笔可在同一章并行交织、一条线跨章推进，提醒与阶段兑现均引用原伏笔而不另建副本，不把scope或建档步骤误当成必须依次完成的剧情。后续滚动补纲沿用同一条长篇审核链，按书纲→卷纲→已确稿章纲→已写正文和新实体候选逐层核对，只新增未来细纲，不重写已有正文或整个结构。首次创建并不生成全书所有详细章纲。滚动批次针对新增有名人物、地点、势力和伏笔要求在已审核章纲中提供逐字来源证据，并先保存为待作者确认的实体档案；作者确认时调用现有对应实体服务建档并验证写回，不能由模型自行确稿。含未确认或被拒的提案的章节在调整/确稿前停止正文调用。大纲页的独立 `/chain/generate-outline` 使用 `long-novel-flexible-outline` 生成待确认候选，不是首次创建的第二条固定规划链。必需节点失败时停止下游并保留原始错误。正文生成走独立的现行写作与质检闭环，具体质量标准以唯一执行标准为准。

## 本地开发

要求 Node.js 22 或更高版本。

首次安装：

```powershell
cd server
npm ci
cd ..\desktop
npm ci
```

开发时**后端独立启动，桌面端沿用原有的一条开发命令**。后端不会由桌面端、Vite、健康检查或 Electron IPC 自动拉起。

终端一，仅启动后端：

```powershell
cd server
npm run start:dev
```

终端二，启动桌面端（Vite 自动编译、启动 Electron 窗口并支持 Electron 热重启；不启动后端）：

```powershell
cd desktop
npm run dev
```

服务端固定使用 `3100`，前端固定使用 `5173`。被占用时明确报错，不自动结束旧服务端、不静默切换端口。Electron 窗口只检查后端健康状态，不负责启动或停止后端。关闭服务端应在对应后端终端按 Ctrl+C；运行中的灵感或小说任务不应被脚本强制清理。

## 本地真实运行验收

### 什么时候运行

`verify-local.mjs` 既可以用于**运行中故障诊断**，也可以用于**最终完整验收**，不要求整本小说全部生成完成。

为了取得运行时项目、章节、生成记录和 Gate 数据，建议执行时保持 Server 正常运行（默认 `http://127.0.0.1:3100/api/v1`）。如果 Server 不可用，脚本仍会生成报告，但只把 `server_unavailable` 作为运行根因，并将题材诊断、执行标准、项目发现和项目检查标记为未执行；不会再把 `project_auto_discovery_failed`、`no_projects_found` 等下游结果误报成独立业务故障。

如果小说生成过程中已经报错，可以立即执行快速诊断，不需要等长短篇全部跑完：

```powershell
node verify-local.mjs
```

该命令不会要求短篇和长篇同时存在，也不会只查 `active` 项目。它会自动检查最近的项目（包括 `creating` / `generation_failed`），并在报告中显示项目状态、结构审计、最近 generation run 及其 `error`。灵感发现无论成功还是全部候选被淘汰，最近一批结果都会写入 `runtime.ideaDiscovery`，其中包含前置来源与同构审查、完整题材卡质量验收的候选证据、通过/淘汰数量与原因，因此即使尚未创建任何项目也能复盘题材阶段。若项目壳未落库，报告仍会标记 `no_projects_found`；此时应先查看 `runtime.ideaDiscovery`。只有灵感诊断本身也不可用时，才需要结合创建页错误信息和 Server 日志定位项目持久化之前的故障。

### 最终完整验收（默认推荐）

当应用里已经分别有一个真实短篇和一个真实长篇，并且两个项目均已激活、至少完成第一章真实生成后，在仓库根目录执行：

```powershell
node verify-local.mjs --full
```

这里不要求整本短篇或整部长篇写完；**第一章真实生成完成即可进入验收**。`--full` 会在运行时检查之外，再执行 Server/Desktop 的 typecheck、unit、acceptance 和 build，因此适合作为最终交付前的完整验收。 `--full` 还要求最新灵感发现审计真实存在、成功状态明确、动态请求数量与交付数量一致、合格数量足额且完整请求墙钟满足当前性能验收要求；验收脚本直接读取唯一执行标准中的当前时限，不再维护独立的旧时间阈值；缺少记录或字段相互矛盾时标记 FAIL。脚本只核查已经发生的真实生成，不主动发起模型请求或创建项目。

不需要手工查项目 ID。默认情况下，脚本会从已激活项目中自动选择最近更新的一个短篇和一个长篇，并把两本书同时写入同一份验收报告。

### 高级/精确指定

需要精确指定某两本书时可覆盖自动选择：

```powershell
node verify-local.mjs --short-project <短篇项目ID> --long-project <长篇项目ID> --full
```

单本兼容模式：

```powershell
node verify-local.mjs --project <项目ID>
```

如果最终验收还要运行 E2E：

```powershell
node verify-local.mjs --full --e2e
```

### 报错时怎么看

下面两个文件不是仓库预置文件，而是每次运行 `verify-local.mjs` 后在本地生成，并覆盖为最新结果：

```text
verification/latest.json
verification/latest.md
```

即使最终 verdict 为 FAIL，这两个文件仍会生成。终端命令返回非 0 只表示验收发现问题，不表示报告生成失败。优先查看 `verification/latest.md` 的“运行问题”；需要完整机器数据时查看 `verification/latest.json`。

快速诊断模式用于定位灵感发现、正在创建或创建失败的项目；创建和恢复期间，同项目未结束的创建任务或模型调用禁止清理、覆盖已有资料，失败恢复必须保留此前已激活的正式项目；最终 `--full` 模式则会把短篇和长篇同时写进同一份报告，并严格检查：项目已激活、项目类型正确、`confirmedStory` 已持久化、恢复审计中无缺失模块或一致性问题、章纲与正文映射有效、第一章正文非空、对应 chapter generation run 成功且 Gate 已通过。报告文件已加入 `.gitignore`，默认只保留最新一次。

## 目录

```text
desktop/              Electron 主进程、前端测试
server/               NestJS API、生成链、质量闭环、SQLite、测试
server/shared/src/执行标准.ts  唯一执行标准
verify-local.mjs      本地验收报告生成器
```

灵感发现记录整次请求墙钟，执行标准规定的墙钟上限仅用于完成后的性能验收；正式运行不因达到目标时间取消、暂停或抛弃在途工作，继续遵循原模型单次超时、物理调用预算、主动取消及完整质量门。超时如实报告真实性能不足，但不能把已过质量审查的故事卡清零。前选审核发现有证据的问题时，先隔离问题身份、保留其余真实合格项；若保留项已经达到本次交付数量，不因原可选预选容量未满而再调用原池重选或重复来源审核，直接进入完整卡独立终审。仅当交付本身未足额、或完整卡终审真正产生缺额时，才使用原有唯一预算化原池优先补位；已有合格卡不重做，全部来源、因果、分类、流派和同构质量门不变。完整卡的首屏追问由服务器继承同一已审前选身份，普通成卡与缺额补位共用此绑定；其它差异说明仍须生成并通过独立终审。世界观来源审核按唯一执行标准区分持续时间、距今时间与事件日期。正文、世界规则和结果字段共用证据分句目录，可直接引用同句中的实际条件；结果验收范围不扩展。逐章生成及局部修复在模型调用前接收与行动审核同源的行动状态判据，长篇章纲继续沿用完整规则。行动审核的结果自证引用按原协议纠错处理，保留真实因果缺口；不把引用错误直接改写成故事事实。大规模章纲审核共享同一可选原文目录，结果清单不重复发送全部行动编号；人物对应的action仅为原文定位提示；场景与人物出现完全相同结果时，合并结果地址仍能指回人物原本的行动字段，不代表该行动已支撑结果。真实因果缺口仍经独立审查及原有本章局部修复处理。 章纲因果审核沿用执行标准QLT-003，服务器按固定结果目录的唯一序号绑定每项结果身份；模型只提交对应行动、条件和结论，协议无效或真实因果缺口均不允许写入大纲，不能通过修复协议默认为内容合格。
