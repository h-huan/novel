# 小说源头质量维护

## 权威与范围
先核验当前分支和 HEAD，读取 README.md、DEVELOPMENT_GOVERNANCE.md 与唯一执行标准 server/shared/src/执行标准.ts 中相关 Rule ID、依赖及消费者；QUALITY_EXECUTION.md 只是旧链接兼容，system-workflow-rules.registry.ts 只是执行标准的重新导出，两者均不得再维护规则正文。本技能组织执行流程，不另定义小说质量阈值或固定套路。应用程序不加载本文件，运行约束通过现有 Registry 缓存与审查合同生效。

## 执行步骤
1. 确认项目、分支、服务版本、运行中任务及已有改动。读取最新日志、当前资料和失败原文，区分系统错误、资料源冲突、正文缺陷与证据未知。
2. 使用 GOV-004 的影响检查，并按 QLT-003 的 SOURCE_QUALITY_POLICY 检查承诺、连续状态、行动主体、专业前提、剧情变化、人物表达六项。同一事实只从当前确认版本消费；缺失字段不从旧档案猜回。
3. 先定位最早引入问题的规则/上下文/来源，修改现有权威条款及实际消费者。只加提示词不足以证明修复；核对解析、质量门、修复路由和保存都能消费结果。涉及作者确认的事实，输出待确认候选及影响，不自动改写作品。
4. 检查章节审查覆盖合同和四项阅读倾向分别返回，有引文及理由。合同不全是审查未完成；关键缺口沿既有门处理，高分不能补偿。文本评分不是实测商业数据，未写章节不算已兑现。
5. 用不同题材与正常反例验证；至少覆盖隐含日常因果、明确交割、缺失权限、状态矛盾、未知专业前提、关系改变的声音。评审合同测试只能证明证据与路由，不能证明模型语义判断正确。
6. 同族失败再次出现时按 RPR-005 回查上游，停止盲目叠加局部修复。保留草稿、原结论和未知项，不降质量门。
7. 新机制替换旧机制时，检查入口、上下文、审查、修复、保存、恢复及关联文档，删掉被替代的旧分支、重复提示词和过时断言；保留数据版本或职责不同的独立质量门。重要流程和规则调整须在同一轮同步检查并更新唯一执行标准、README、DEVELOPMENT_GOVERNANCE、适用的 API/使用文档及测试，不另复制一份规范。缺项明确列为未完成。
8. 运行相关合同/源头/类型测试。真实失败回放如需外发新日志，按当前用户授权执行；未回放标未验证。重启前检查运行中任务，构建后验证服务版本、前端和API健康。

## 交付
报告规则ID、版本、消费者、影响范围、证据、验证结果与未验证项。区分技能文件完成、运行机制完成和真实模型效果验证；不以绿测代替全链路结果。Git 修改、提交和推送以当前用户授权及 DEVELOPMENT_GOVERNANCE.md 为准，不擅建分支、合并 main 或将未验证标记为完成。
