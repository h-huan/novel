# 正文质量与质检体系问题诊断报告

> 诊断对象：novel-ai-platform（《我在乱世召唤玩家》AI 写作平台）
> 诊断时间：2026-08-12
> 诊断方式：代码全链路分析（server/ + desktop/）+ 联网行业研究（番茄/起点爆款特征、AI 文通病、LLM 长上下文机制）
> 结论性质：**只诊断、不改代码**。所有结论附代码证据（文件:行号）。

---

## 一、结论摘要

平台的"不好用"不是单一 bug，而是**三层结构性缺陷叠加**：

1. **质检体系割裂**——多达 6 套质检机制分散在 6 个服务里，各查各的、互相覆盖、标准不一、前端无统一视图。作者感受 = "查了跟没查一样"。
2. **正文生成"合规驱动"而非"好看驱动"**——prompt 塞了 45+ 条"禁止 X"规则（约 200 行），触发了 LLM 的 Lost-in-the-Middle 效应，中段规则被遗忘；且全是禁止性约束，几乎没有正面示范和风格锚点。作者感受 = "像 AI 小说"。
3. **上下文工程缺失**——角色只取前 8 个、状态只取最近 1 条、无关键信息排序、无前文因果链约束。作者感受 = "前后没联系、内容凭空出现"。

## 三、问题 1：质检体系割裂（详细证据）

### 3.1 致命细节：质检结果互相覆盖

`consistency_checks` 表被 **两条独立写入路径** 共享，且删除逻辑不对称：

- **路径 A（LLM 验收器，生成时）**：`chain.controller.ts:1052`
  ```sql
  DELETE FROM consistency_checks WHERE project_id = ? AND chapter_index = ? AND source = ?
  ```
  ✅ 带 `source` 过滤，只清自己的记录，再写入 `source='alignment_verifier'` 的矛盾。

- **路径 B（确定性检查，保存章节时 / 手动触发）**：`consistency-check.service.ts:280`
  ```sql
  DELETE FROM consistency_checks WHERE project_id = ? AND chapter_index IN (...)
  ```
  ❌ **不带 source 过滤**。任何一次 `checkConsistency()` 都会把该章节**所有来源**的历史矛盾（包括 LLM 验收器刚写入的）**全部删除**，然后只插入自己的检查结果。

**触发链**：作者保存章节 → `chapter-derived-data-sync.service.ts:104` 调 `runConflictReview` → `checkConsistency()` → `saveChecks()` 无差别清表。

**用户可感知的后果**：生成正文时 LLM 验收器明明报出"3 处大纲矛盾"，作者一保存章节，矛盾列表被清空或只剩关键词检查结果——"刚才的矛盾去哪了？"这就是割裂感的第一来源。

### 3.2 确定性检查名不副实（4 个检查全是"过家家"）

`consistency-check.service.ts` 的四个检查：

| 检查 | 实现方式 | 实际能力 |
|------|---------|---------|
| 人物一致性（:321-337） | 4 对固定反义词（勇敢/胆小、正直/狡诈、善良/邪恶、乐观/悲观）做 `content.includes()` | 无法识别任何真实 OOC；正文写"他不再胆小"也会误报；性格标签从 JSON 解析后仅做词面匹配 |
| 世界观一致性（:169-188） | 从 `rules` 里提取"禁写词"做子串匹配 | 这是**关键词过滤**不是一致性检查；世界观规则里没有"禁写词"字段就完全查不到 |
| 时间线一致性（:196-220） | 只检查 `chapter_index` 序号是否连续 | 不读正文中的时间表述（"三天后" vs 前文"三个月后"完全无感） |
| 情节逻辑（:225-268） | 只检查章节是否绑定了 outline_id + 伏笔是否超回收期 | 不检查因果链、动机链、事件逻辑 |

### 3.3 六套质检各自为政

| # | 质检机制 | 位置 | 检查内容 | 触发时机 | 结果去向 |
|---|---------|------|---------|---------|---------|
| 1 | `checkChapterAlignment`（LLM 验收器） | `chain.controller.ts:663-784` | 大纲对齐/连续性/人物/世界观/时间线/文笔 6 维度 | 生成后 | `consistency_checks`(source=alignment_verifier) |
| 2 | `detectForbiddenTells`（硬红线扫描器） | `chain.controller.ts:1109-1580` | 45+ 确定性规则（排比/比喻密度/对话比等） | 生成后 | 注入验收器 + `consistency_checks`(source=hardline) |
| 3 | `QualityGateService`（三级质量门） | `quality-gate.service.ts` | Rule 检查 + LLM Judge | 链式节点 | 独立 result 对象，**不入库、前端无展示** |
| 4 | `ConsistencyCheckService`（确定性检查） | `consistency-check.service.ts` | 4 项关键词检查 | 保存章节/手动 | `consistency_checks`(无 source) |
| 5 | 各模块 `checkConsistency` | `character.service.ts:463` / `world-setting.service.ts:161` / `map-point.service.ts:72` | 各自独立的关键词规则 | longWrite/generate 后 | 仅 console/返回体，**不入库** |
| 6 | `conflict.controller.ts`（矛盾引擎） | `conflict-engine/conflict.controller.ts` | 只读 `consistency_checks` 做展示/P0 升级 | - | 前端矛盾 tab |

**架构级缺失**：
- 无统一编排器：一次生成触发 2/4/5 三处，没有一处生成"完整质检报告"。
- 无统一数据模型：3/5 的结果不入库，作者永远看不到。
- 无跨章维度：没有任何机制检查"伏笔链跨章是否自洽""角色动机链是否连贯""世界观规则在后续章节是否被遵守"。

### 3.4 QualityGate 形同虚设

`quality-gate.service.ts:276-301`：
```ts
let score = 85;                       // 默认 85 分
if (outputText.length < 50) score -= 20;
if (output.title || output.content) score += 5;   // 有字段就加分
if (criterion.name.includes('完整')) {
  if (output.outline || output.chapters) score += 5;
}
```
- 所有 criterion 共用同一套"字段存在性"检查，**criterion 的具体语义（如"情感真实""节奏紧凑"）完全不参与评分**。
- 85 分默认值 + 有 title/content 就 +5 → 大多数内容无脑通过。
- `evaluateByLLM` 的 Judge prompt 只用 `criterion.name/description/minScore` 泛化拼接，没有把评分标准的具体要求注入 Judge。

### 3.5 半自动模式是"假功能"

`writing-mode.service.ts:805-831`，注释原文："**模拟**：发出确认请求给用户"、`aiOutput: '将在每个节点执行后请求确认'`，随后**不等待用户**直接 `return this.chainEngine.execute(chain, userInput)`。
→ 用户选了"半自动/逐节点确认"，实际拿到的是全自动结果，且 UI 上挂了虚假的确认请求。

## 四、问题 2：正文"AI 味"的根因

### 4.1 核心根因：Prompt 过长触发 Lost-in-the-Middle（有量化证据）

`buildOutlineAdherenceContract`（`chain.controller.ts:7325-7528`）构造约 **200 行、45+ 条规则** 的超长约束。而 LLM 长上下文注意力是 **U 型曲线**（联网研究量化数据）：

| 模型 | 开头准确率 | 中间准确率 | 结尾准确率 |
|------|-----------|-----------|-----------|
| GPT-4 | 87% | **52%** | 83% |
| Claude 3 | 89% | **58%** | 85% |
| Llama 3 70B | 82% | **43%** | 78% |
| Gemini 1.5 | 85% | **55%** | 82% |

> 上下文越长 U 型越严重：4K 上下文中间准确率约 55%，128K 时掉到 30%，1M 时仅 15-20%。

**代码自己都承认了**（`chain.controller.ts` 相关注释）："LLM 在长 prompt 下经常只记住开头与结尾、把中段规则遗忘"。但 45+ 条规则仍全部前置堆在 prompt 中段——**明知会忘，还是塞进去，等于没写**。

**用户可感知后果**：排比（规则 33/34 在中间被遗忘）、形容词堆砌（规则被遗忘）、逻辑断裂（规则被遗忘）——正是主公反馈的现象。

### 4.2 全是"禁止 X"，没有"应该 Y"

- 45+ 条规则中，除 21-25 条外，几乎全部是禁止性描述（"不得使用排比""禁止过度形容词"）。
- **正面示范缺失**：没有"目标风格"的示例段落、没有"好的排比 vs 坏的排比"对比、没有"上等网文段落"的锚点。
- 行业共识（联网研究）：**"示例胜于描述"（few-shot）是风格模仿最有效的手段**——"告诉 AI 画蓝色的东西"远不如"给它看确切的色调"。抽象地禁止 AI"别写 AI 味"，AI 不知道什么叫"人味"。

### 4.3 无网文市场特征约束

对照番茄/起点爆款的确定性特征（联网研究），平台生成约束中**完全没有**：

| 爆款特征 | 平台现状 |
|---------|---------|
| 开篇 300 字内出冲突/钩子（78% 读者 3 秒弃书） | 无约束 |
| 每 3 章一个小爽点、每 10 章一个大高潮 | 无约束 |
| 每章结尾留悬念（追更率核心） | 无约束 |
| 打脸通过"旁观者震惊"呈现、不自嗨 | 无约束 |
| 章节功能（铺垫/推进/高潮）区分 | 大纲有 `chapter_function` 字段但生成约束未强制 |
| 日更节奏下的信息密度控制 | 无约束 |

### 4.4 模型与采样参数一刀切

`route-config.json` 所有写作场景 → 同一个 `deepseek-chat`。行业实践（联网研究）：文学创作需要 **temperature 0.6-0.9** 才能出"意外的比喻与措辞"，推理/规划场景才用低温。当前所有场景同参数，正文必然"安全但平庸"。

### 4.5 降 AI 味规则覆盖不全

现有 `detectForbiddenTells` 已覆盖：排比/比喻密度/破折号密度/时间词密度/列举/对话比。但行业公认的 AI 高频特征**未覆盖**：
- 填充词密度：微微/轻轻/不由得/仿佛/似乎/宛如（"删掉 60% 的微微轻轻不由得"是降味第一招）
- 句式重复："他知道…他明白…他清楚…"同构连用
- 段落长度均匀度：AI 默认 3-5 句一段
- 一句话堆 3 个比喻、4 个形容词的信息密度
- 连接词滥用：然而/因此/与此同时/随即

## 五、问题 3：前后断裂、内容凭空出现的根因

### 5.1 上下文构建"多多益善"但"无脑堆叠"

`buildAutoContext`（`chain.controller.ts:7547-7612`）：
- 角色只取 **前 8 个**，多角色项目后半角色完全不在上下文中 → 后出场角色凭空出现。
- 角色状态从 `character_state_history` 取**最近 1 条**，若该条已过期（中间隔了几章没更新）→ 用旧状态生成 → 前后矛盾。
- 未按"本章相关度"排序上下文 → 关键设定埋在中间，被 Lost-in-the-Middle 吃掉 → 该用的设定没用上，新设定凭空出现。

### 5.2 无"承接前文"的强制机制

- 生成前没有"读取上一章结尾 + 输出 3 条必须承接的点"的步骤 → 每章都是"从零开始"，前后无钩连。
- `checkChapterAlignment` 虽有 `continuityPassed` 维度，但 LLM 验收器的判定是"事后找茬"而非"事前约束"，且结果可能被 §3.1 的互踩逻辑清掉。

### 5.3 跨章因果链无人检查

- 伏笔：只查"是否超回收期"，不查"埋设→激活→回收"的链条是否自洽、证据是否对得上。
- 角色动机：只查 4 对反义词，不查"动机强度是否随情节推进合理演化"。
- 世界观规则：只查禁写词，不查"规则 A 在第 3 章生效、第 15 章被打破是否有人解释"。

## 六、解决方案（按优先级）

### P0-1 修掉质检互踩（一行级修复 + 机制补强）

1. **立即修复**：`consistency-check.service.ts:280` 的 DELETE 加上 `AND source = ?`（或改用 upsert 按 source 分组）。
2. **机制补强**：引入"来源归并 + 快照保留"——同一章节的质检结果按 `(chapter_index, source)` 保留最新快照，不同 source 永不互删；矛盾列表展示时按 source 分组显示（LLM 验收 / 硬红线 / 确定性 / 质量门），作者一眼看到"这章有 3 处 LLM 验收矛盾 + 1 处硬红线违规"。

### P0-2 统一质检编排器（Quality Orchestrator）

新增单一入口（如 `chain.controller` 内部编排函数或独立 service），生成完成后**一次调用**串起：
`detectForbiddenTells（硬红线）→ checkChapterAlignment（LLM 验收）→ ConsistencyCheckService（确定性）→ 各模块 checkConsistency（合并）→ QualityGate（质量门）`，
产出一份**统一的质检报告对象**：按章节聚合、按严重度分级、附证据与建议动作，全部落库（统一 `consistency_checks`，各带 source）。
→ 消灭"6 套机制各报各的、一半结果不入库"的现状。

### P0-3 生成 Prompt 重构（降 AI 味的核心）

1. **规则瘦身**：45+ 条 → 保留 8-10 条"不可协商硬约束"（排比/形容词堆砌/逻辑断裂/凭空出现等），其余删除或降级为可选项。
2. **位置工程**（对抗 Lost-in-the-Middle）：
   - 最关键的 3 条硬约束放 **Prompt 最末尾**（模型注意力最强处）；
   - 上下文设定放开头；
   - 中段只放"参考信息"，不防关键指令。
3. **正面示范 > 禁止列表**：为每个写作风格配 2-3 段**风格锚点示例**（作者确认过的好段落 / 对标作品片段），用 few-shot 让模型"看到确切色调"而不是"听懂抽象禁令"。
4. **加入网文节奏约束**（若项目目标平台为番茄/起点）：开头 300 字出冲突、每章结尾留悬念、本章功能（爽点/铺垫/高潮）来自大纲 `chapter_function` 字段强制写入。
5. **写作前自检清单**：生成前先输出 3 条"本章必须承接的前文事实 + 本章唯一核心冲突"，再写正文（CoT 锚定，防凭空出现）。

### P0-4 半自动模式去模拟化

`executeWithConfirmation` 改为**真实现**：每节点执行完，通过 SSE 向写作页推送确认请求（复用现有 `onUserConfirmation` 通道），**挂起等待**用户"通过/调整/重生成"回调后才进入下一节点。在没实现前，UI 上禁用半自动选项，绝不展示假的确认流程。

### P1-1 确定性检查升级为"语义检查"

- 人物一致性：用 LLM 语义判断替换 4 对反义词子串匹配（"性格标签 vs 本章行为是否冲突"），保留关键词扫描做快速初筛。
- 时间线：解析正文时间表述（"三天后/次年/黄昏"）与章节序号的交叉验证。
- 世界观：从 `rules` 提取"规则内容"（而非仅"禁写词"），LLM 判断正文是否违反。
- 跨章因果链（新增维度）：伏笔埋设→激活→回收链条自洽性、角色动机演化合理性、世界观规则跨章遵守度。

### P1-2 上下文工程改造

- **关键信息排序**：按"本章大纲相关性"重排上下文，最相关设定放开头/结尾，整体控制在 4-6K tokens（宁可少而准，不要多而乱）。
- **角色状态快照**：取最近 N 条 `character_state_history` 合成"当前状态"，而非最近 1 条。
- **承接前文步骤**：生成前强制读取上一章结尾 300 字 + 前 3 章摘要 + 未回收伏笔清单，输出"本章必须承接的 3 点"后开始生成。
- **全量角色注入**：移除"前 8 个"截断，改为按本章出场概率检索（已有向量索引可复用）。

### P1-3 模型与参数参数化

- `route-config.json` 拆分写作场景温度：正文生成 0.6-0.9（按风格类型细分），质检/规划 0.2-0.4。
- 若平台支持多模型，正文写作路由到文学能力更强的模型（deepseek-chat 保留给质检/策划场景）。

### P1-4 降 AI 味规则补齐（确定性扫描器扩展）

补充行业公认但未覆盖的规则：
- 填充词密度（微微/轻轻/不由得/仿佛/似乎/宛如）
- 同构句式重复（"他知道…他明白…他清楚…"）
- 段落长度标准差（均匀度过高报警）
- 单句比喻/形容词堆叠密度
- 连接词滥用（然而/因此/与此同时/随即）

### P2-1 前端统一质量总览

- 矛盾 tab 支持按 source/类型/严重度筛选，显示各来源计数徽标；
- 新增"本章质检总览"卡片：大纲对齐 / 硬红线 / 设定一致性 / 质量门 一次看全，附"已解决 / 未解决"状态；
- 生成结果横幅与矛盾 tab 的计数改为读统一质检报告，杜绝"弹框说有矛盾、tab 里没有"的错觉。

### P2-2 好文标准落地（对标本平台目标）

- 项目级"目标平台"配置（番茄/起点/知乎盐选…）→ 决定节奏约束与质检权重；
- 质检维度从"合规"扩展到"可读性"：钩子强度、代入感、悬念延续、爽点密度——由 LLM Judge 用具体评分标准（而非字段存在性）评分。

## 七、对照：百万阅读网文的可量化特征（联网研究结论）

来自番茄/起点爆款方法论与平台数据（2024-2026）：

1. **开篇定生死**：78% 读者 3 秒内决定弃书；前 300 字必须出冲突/钩子；第一章出金手指或生死危机的作品留存率比平淡开篇高 40%。
2. **黄金三章**：第一章立人设+抛悬念，第二章展示能力/打脸，第三、四章借"旁观者震惊"加深渲染（自嗨式描写是毒点）。
3. **节奏密度**：每 3 章一个小爽点、每 10 章一个大高潮；每章结尾留悬念；旧冲突解决的同时必须抛出新悬念（期待感不能断层）。
4. **代入感 + 期待感**：代入感=快速进入主角视角；期待感=危机或"拉跨异能无人识货"式的延迟满足。
5. **完读率/追更率是算法唯一硬指标**：追更率 40% 以上作品流量倾斜是低追更的 5 倍；10 万字完读率 15% 才算及格。
6. **AI 文是平台整治对象**：2025 年番茄提高签约门槛、加重低质水文处罚——"AI 味"直接关系商业收益。

**AI 文可检测特征清单**（供质检/降味双重使用）：
- 语言：高频安全词重复（同一情绪词 500 字内 >5 次）；形容词并列堆砌（"更深更沉""沉痛而悲伤""无奈但释然"）；夸张的"非人感"比喻（砂纸磨过嗓子/火焰窜过血管）；喜欢数字"3"。
- 句型：断句过分规整、主谓宾齐全、无倒装插入语；短句连用（几个字一个句号）；节奏无呼吸、无作者语癖。
- 逻辑：点对点能力（有开头有梗，无由点到线到面的长线能力）；只抛梗不回收；每段节奏不错但跟主梗割裂；吃书；不合生活常识。
- 情感：标准化概括（"他非常悲伤"）而非细节展现（"他攥紧口袋里的旧照片，指尖泛白"）；所有角色情感反应同一套流程。

**降 AI 味 7 招**（可转化为后处理/重写 prompt 指令）：
1. 打散段落节奏：某段只 1 句、下段 8 句，模拟人类思绪。
2. 删掉 60% 的"微微/轻轻/不由得"。
3. 加入口语化破句："他不想听。真的不想。一个字都不想。"
4. 加入"无意义但真实"的细节："他从口袋里摸出半包烟，发现还剩一根。点上，发现打火机没气了。"
5. 把 AI 高频比喻替换成与人物背景相关的自定义比喻。
6. 手改对话：人话有省略、有口头禅、有打断，AI 对话太"完整"。
7. 段落长度刻意不均（AI 默认 3-5 句一段是检测点）。
